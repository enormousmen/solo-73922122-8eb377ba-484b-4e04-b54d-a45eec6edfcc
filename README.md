# 切片值班台（常规底图 / 应急航片 · 应急插队 · MBTiles 导入）

FastAPI + Pillow 的切片演示服务：内置常规底图、应急航片各一张（2048×2048，启动时自动生成），
值班员可分别启动切片、查看进度、打开已发布的 PNG 瓦片；应急任务受理后立即抢占常规渲染。
常规底图还支持上传别处切好的 **MBTiles 包**：验包通过后只补空位，已有的瓦片一律不覆盖。

## 快速开始

```bash
docker compose up --build
# 打开 http://localhost:8000
```

本地开发（Python 3.11+）：

```bash
pip install -r requirements.txt
DATA_DIR=./data TILE_DELAY=0.15 python -m app.cli
# 或：DATA_DIR=./data TILE_DELAY=0.15 uvicorn app.main:app --host 0.0.0.0 --port 8000
```

环境变量：`DATA_DIR`（源图/瓦片/日志/上传暂存目录，默认容器内 `/data`）、
`TILE_DELAY`（每张瓦片模拟渲染耗时秒数，默认 0.15）、
`IMPORT_VERIFY_DELAY`（每张导入瓦片的模拟验包耗时秒数，默认 0，调大可观察"验包期间照常切片"）。
`PORT` 可改监听端口；多 worker（`WEB_CONCURRENCY`/`UVICORN_WORKERS` > 1）会被拒绝。

## 页面演示

### 渲染到一半插队

1. 点「启动切片」→ 常规底图进度条开始推进，瓦片逐张点亮；
2. 渲染到一半时点「启动应急切片（插队）」→ 常规立即变为「被抢占·待续算」，应急开始渲染；
3. 应急完成后常规自动续做（本轮计划数 = 剩余未发布张数，已发布的不重算）；
4. 勾选「模拟渲染失败」再启动应急，可演示应急失败后常规照常续做；
5. 点击任意已点亮瓦片可在新标签页打开对应 PNG；「重置」清空该任务已发布瓦片（任务空闲时才允许）。

### 导入 MBTiles

1. 点「下载本地样包」得到 `samples/regular-partial.mbtiles`（22 张，含 z0–z3 的若干坐标）；
2. 选择该文件点「上传并验包」。可先点「启动切片」让常规渲染到一半——
   验包期间切片和取图照常进行；
3. 验包通过后只补空位：样包里已有坐标若已被切片发布，则跳过且不覆盖；
   导入的坐标立即计入进度（按实际出图坐标计），后续切片跳过它们；
4. 「重置」常规会清空瓦片，并使正在验包/导入的包作废；
5. 勾选「模拟写盘中途失败」再上传，可演示写盘中断：已发布的完整瓦片保留，提示可重传，
   重传只补剩余空位。

## MBTiles 验包规则

- 单包 **≤ 8 MiB**（超过返回 413）；
- `metadata.format` 必须为 `png`，`metadata.source_sha256` 必须等于**常规源图当前文件的 SHA-256**；
- 只收 **z0–z3** 的 **256×256 PNG**；MBTiles 行号自南向北，本站自北向南，
  换算 `y = (2^z - 1) - tile_row`；
- 整包**先完整解码全部瓦片**再落盘：坐标越界、坐标重复（换算后）、任一瓦片无法完整解码
  （含截断、非 PNG、尺寸不符）→ **整包拒收**，不写入任何瓦片；
- 通过后**只补空位**：目标坐标已有文件则跳过，导入和渲染都不覆盖（以先发布的文件为准）；
  发布用"临时文件 + 不覆盖原子发布"（优先硬链接），读者不会读到半成品；
- 验包期间照常切片与取图；若验包期间常规任务被**重置**，此包**作废**；
- 写盘中途失败时保留**已发布的完整瓦片**并提示可**重传**，重传只补剩余空位。

## 实现内容

- **任务模型**（`app/scheduler.py`）：常规 / 应急两个任务，各 85 张瓦片（z0–z3，256px）。
  状态机：`idle → queued → running → done / failed / interrupted`；`interrupted` 的常规任务在应急结束后被调度器自动续做。
- **单渲染子进程**：调度主循环串行执行 `_run()`，同一时刻最多一个 `worker.py` 子进程；
  应急受理时若常规在跑，先中止旧进程并 `await proc.wait()`，确认退出后才启动应急进程。
- **抢占协议**：父进程向子进程 stdin 写 `ABORT` 指令（worker 用 `select` 监听 stdin，
  渲染睡眠可被立即唤醒，收到指令或 EOF 即以约定退出码 42 退出），同时补发 SIGTERM 双保险。
  不依赖信号即可工作（某些沙箱环境禁止 kill），正常 Linux / Docker 中两条通道都有效。
- **不覆盖发布**（`app/tilefs.py`）：worker 与导入器都先写同目录临时文件，
  再以 `os.link`（目标已存在即失败）原子发布；不支持硬链接的卷退化为 `open(..., "xb")` 独占创建拷贝，
  失败时删除半成品。被中止时当前瓦片尚未发布，残存的临时文件由下次 worker 启动时清理。
- **导入器**（`app/imports.py`）：上传体先限长读入内存（≤8 MiB），再落盘到 `DATA_DIR/uploads` 暂存，
  后台线程只读打开 SQLite 逐张完整解码；全部通过后才开始逐张"只补空位"发布。
  发布时与重置使用同一把 `RLock`，并用重置计数（epoch）判断作废；
  每发布一张通过线程安全回调同步给调度循环，进度立即反映。
  同一时刻只受理一个包（重复上传返回 409）。
- **应急失败钩子**：`POST /api/jobs/emergency/start?simulate_fail=true`，worker 发布 10 张后以退出码 3 模拟崩溃，用于自测与演示。
- **写盘失败钩子**：`POST /api/import/mbtiles?import_fail_after=N`，导入成功发布 N 张后模拟写盘中断（页面以勾选项触发）。
- **API**：
  - `GET /api/status` 两任务进度快照（状态、百分比、在渲瓦片、本轮计划、已发布清单）+ 最近一次导入包状态；
  - `POST /api/jobs/{kind}/start`（kind=regular|emergency，幂等；emergency 支持 `simulate_fail`）；
  - `POST /api/jobs/{kind}/reset`（任务进行中返回 409；重置常规会作废在途导入包）；
  - `POST /api/import/mbtiles`（multipart 字段名 `file`；支持自测参数 `import_fail_after`）；
  - `GET /api/import/{id}` 单次导入状态；
  - `GET /tiles/{kind}/{z}/{x}/{y}.png`（未发布 404）；
  - `GET /samples/regular-partial.mbtiles` 下载内置样包；
  - `GET /sources/{kind}.png` 源图预览；`GET /` 演示页面。
- **样包**（`samples/regular-partial.mbtiles`，22 张）：由常规源图切出，`source_sha256` 与源图一致；
  服务启动后若发现仓库内样包与**当前**源图哈希不符（例如不同 Pillow 版本的 PNG 编码差异），
  会自动按当前源图重建一份到 `DATA_DIR/samples/` 并通过该路由提供，保证演示样包始终能过验包；
  重新生成：`python scripts/make_samples.py`（默认用 `data/sources/regular.png`，缺省会先生成源图）。
- **源图**（`app/sources.py`）：启动时用 Pillow 生成两张 2048×2048 区分度高的测试图（渐变 + 网格 + 坐标标注），已存在则不覆盖。

另手工核验（同一轮开发中执行的脚本，均通过）：

- 拒收细分：`format` 非 png、SHA 不符、越界、z4、128×128、重复坐标、截断 PNG、非 SQLite、空包
  全部拒收且目录内瓦片数不变；>8 MiB 返回 413；
- 导入坐标的像素与 worker 从同一源图切出的瓦片逐像素一致（校验了南向北行号换算方向）；
- 导入与切片并发时，worker 不会覆盖导入发布的文件（比对 mtime 全部未变），无残留临时文件；
- `GET /`、`/app.js`、`/style.css`、`/samples/regular-partial.mbtiles`（attachment）均 200；
- 已发布瓦片 200 且为合法 PNG，未发布瓦片 404；未知导入 id 返回 404；并发上传第二个包返回 409；
- 复跑：`BASE=http://127.0.0.1:8000 DATA_DIR=./data python3 scripts/selftest.py`。

## 未完成项 / 说明

- 本交付环境无 Docker 守护进程，`docker compose up --build` 未在本机实际构建执行；
  Dockerfile / compose 为标准写法，应用本体已在容器外以相同命令（`python -m app.cli` 单进程）实测通过。
- 调度与导入状态在内存中，必须单 uvicorn worker 运行（入口已拒绝多 worker）；
  服务重启后已发布瓦片保留，但未完成任务需重新启动，最近一次导入记录不保留
  （上传暂存目录中的残留文件会在启动时清理）。
- 上传包整包读入内存后再验包（上限 8 MiB，按此上限设计）；未做流式解析。
- 验包为顺序逐张解码，包越大耗时越长；未做逐张并行。
- `IMPORT_VERIFY_DELAY` 仅用于演示节奏，真实验包耗时为 0。
- 渲染耗时用 `TILE_DELAY` 模拟，未接真实切图负载；瓦片方案为单源图 z0–z3 固定金字塔
  （源图 2048×2048 恰为 z3 的 8×8），未做通用 XYZ 坐标系对齐与多比例尺重投影。
- 未做鉴权与并发操作限流（重复启动幂等，重置仅做空态校验，导入一次只受理一个包）。
